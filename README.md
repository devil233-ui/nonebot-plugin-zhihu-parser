## 配置项
```
# 单次解析最多输出的图片/视频总量阈值
ZHIHU_MAX_IMAGES = 20
# 合并转发的单批次图片最大数量（推荐 5~10）
ZHIHU_BATCH_SIZE = 5
# 同一个链接的冷却时间（单位：秒。86400秒 = 24小时）
ZHIHU_DEBOUNCE_TIME = 86400
# 自动清理多久以前的缓存文件（单位：秒。604800秒 = 7天）
ZHIHU_CACHE_MAX_AGE = 604800
# ck
ZHIHU_COOKIE=""
```

## 登录保活与失败提醒

- 自动保活沿用原来的日期安排，按机器人配置的时区在凌晨4点后随机延迟最多15分钟，
  不再每次都卡在整点执行。这是错峰措施，不保证避免平台风控。
- 连续两次保活失败后发送提醒，同一次故障只提醒一次；成功后重新开始计数。
  计数和送达状态保存在插件数据目录，重启不会清零。
- 通知未送达时保留待发状态，在机器人重新连接或下次保活时补发；
  已送达的接收人不会重复收到同一故障的提醒。
- 未指定接收群时，默认私聊现有的机器人管理员，不会向所有群广播。
  指定群后只通知配置的目标；同时配置私聊账号时，两类目标都会收到提醒。
- 管理员可发送“知乎保活”手动刷新，直接看到成功或失败原因；
  非管理员不能触发登录信息刷新。登录失效需要重新登录，保活不能替代登录。

可选配置（与现有配置放在一起，修改后重启机器人生效）：

```dotenv
# 提醒接收群；留空不发送群提醒
ZHIHU_REFRESH_ALERT_GROUPS = []
# 可选：指定私聊接收账号，显式设为空列表可关闭默认管理员私聊
# ZHIHU_REFRESH_ALERT_USERS = []
# 随机延迟上限，单位秒；默认900，允许0到3600
ZHIHU_REFRESH_JITTER_SECONDS = 900
```

解析和保活共用同一份浏览器身份；保活请求设有超时限制。
刷新失败不会写回响应中的空登录信息，刷新期间手动更新的登录信息也不会被覆盖。
不要将Cookie、刷新令牌或完整响应内容发送到群聊、日志或提交到仓库。

## 已知问题

目前测试所谓任意风控部分均可通过单独发送解决，其实并不能确定是风控引起的；又，最初测试过一个批次输出50张图都能顺利，可以排除体积原因。

这个奇妙风控在原项目同样存在（但没有备用方案），所以总之目前本项目只能通过独立发送解决这个问题，希望有高人指点。
